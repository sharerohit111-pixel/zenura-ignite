# ZENURA IGNITE Paper Trading — Supabase migration design

Status: **Draft only. Not applied to Supabase.**
Working branch: `migration/supabase-paper-trading-schema-draft-2026-11-22`
Baseline branch: `integration/paper-trading-backend-main-2026-11-20`

## Scope and safety

This is only the first relational schema draft for the existing Paper Trading module. It does not change the live frontend, Firebase project, Cloud Run service, production credentials, or existing PR #28. The old backend remains the rollback source until parity tests and a separately approved cutover.

Paper Investing is out of scope. No real exchange/broker order is submitted by this simulator.

## Existing behavior verified in the integration branch

- Gateway: `market-gateway/server.js`, Node.js 22, Express, deployed as a long-lived Cloud Run service for Upstox Market Data Feed V3.
- Authentication: gateway verifies Firebase ID tokens with revocation checking.
- Firestore collections directly used by the gateway: `upstoxConnections`, `indianPaperAccounts`, `indianPaperOrders`, `indianDerivativeOrders`, and `indianMarketWatchlists`.
- Other server-managed Firestore state is referenced through helpers for stream leases and futures margin-preview cooldowns.
- One shared INR virtual cash balance is used across cash equities and long-option simulations. Starting capital is ₹10,00,000 (100,000,000 paise).
- Cash-equity positions are separated into Delivery (`positions`) and Intraday (`intradayPositions`); share reservations are separated too. Pending LIMIT BUY reserves shared cash. Current API explicitly rejects Intraday LIMIT orders.
- Long CE/PE BUY and SELL-to-close are supported. Futures margin preview is informational only; futures execution, short options, and real broker orders remain disabled.
- Watchlists are per-user, named `My Stocks`, `Banking`, `NIFTY`, `F&O`, maximum 50 instrument keys each.
- Existing cash-equity order IDs are SHA-256 of user UID plus UUID idempotency key. The inspected Firestore order payload persists the SHA-256 request fingerprint but does not persist the original UUID idempotency key. Therefore the draft makes `idempotency_key` nullable for imported legacy rows, preserves the original 64-character `order_id`, and adds a partial unique index for keys generated by the new backend. Request fingerprints preserve the legacy Delivery payload.
- Upstox token ciphertext is decrypted only in trusted server code; plaintext access tokens must never reach the browser.

## Important design decisions

1. Store all money as integer paise; do not use floating-point numeric values for trading arithmetic.
2. Preserve the single ₹10 lakh shared cash account; do not grant ₹10 lakh separately to Delivery, Intraday, and Derivatives.
3. Keep Delivery and Intraday equity holdings separate. Keep long-option holdings in a separate table.
4. Preserve idempotency key and fingerprint uniqueness per user. Never create a second fill on a retry.
5. Keep Upstox token ciphertext, OAuth state, stream leases, and rate-limit state inaccessible to browser roles.
6. Enable RLS on all user-data tables. Browser roles receive read access to own account/history/positions and own watchlists only. Trading writes are reserved for a trusted server runtime.
7. The Upstox WebSocket gateway is long-lived; it must not be moved blindly into a short-lived Edge Function. Keep a dedicated supported runtime for streaming.
8. Keep Firebase as the authentication provider using Supabase's hosted Firebase third-party Auth integration. Firebase UID values are strings, so do not cast them with auth.uid() or create duplicate Supabase Auth users. Each Firebase UID maps to a stable internal relational UUID in paper_user_identity_map; RLS resolves the verified JWT sub claim through a narrowly scoped SECURITY DEFINER helper.
9. Existing Firestore documents need an export/transform/import rehearsal and count/checksum reconciliation before cutover.

The SQL keeps the idempotency key nullable for imported legacy records and uses partial unique indexes for new records if/when the new service persists keys.
- The first-pass SQL had a trailing comma in the derivative-order table definition; this is fixed in the draft.

## OAuth and worker lifecycle audit

The Upstox Firebase implementation is in `functions/indian-market.js`, not in the market-gateway HTTP server. It was inspected along with its helper modules. The migration draft now additionally represents:

- OAuth state lifecycle: state is generated from 32 random bytes, expires after 10 minutes, is atomically marked used before token exchange, and carries a connection generation. The Supabase design stores a hash of the raw state rather than the raw state itself.
- Connection generation control: disconnect deletes the encrypted connection, revokes the active stream lease, and increments a generation so a late OAuth callback cannot re-connect an account after disconnect.
- Connection metadata: connected status, AES-256-GCM token envelope, token type, provider, authorization time and expiry.
- Market stream lease lifecycle: epoch-millisecond expiry/update fields and a revoked flag.
- Pending LIMIT worker cursor: the Firebase worker stores its scan cursor in `indianMarketWorkerState/pendingLimitOrders`; a server-only worker-state table is included, with a partial index for pending LIMIT orders.

The OAuth callback and disconnect operations require multi-row atomic behavior. The eventual Supabase implementation must use trusted server-side RPC/transaction functions and must not expose OAuth state, connection controls, worker cursors, encryption envelopes, or secrets to authenticated browser clients.


## Runtime boundary and deployment implications

The existing market gateway is a Node.js 22 Express service using `ws` for the Upstox v3 WebSocket feed and Server-Sent Events for browser delivery. It also performs instrument-master refresh, quote validation, portfolio valuation, and scheduled LIMIT execution is handled separately by a Firebase scheduled worker.

Supabase Postgres, Auth, Storage, Realtime and Edge Functions provide the database/auth/API building blocks, but the database itself is not a replacement for the long-lived Node WebSocket/SSE gateway. The migration must preserve this runtime boundary:

1. Supabase Auth + Postgres become the identity and persistent data layer.
2. Supabase Edge Functions or a trusted Node API handle short request/response actions such as OAuth start/callback, account reads, order submissions and watchlists.
3. The Upstox WebSocket/SSE gateway and scheduled LIMIT worker remain a separately deployed server process/worker on a container-capable runtime. It may be moved off Google Cloud only after a replacement host passes WebSocket reconnect, lease renewal, backpressure, quote freshness, secrets, scheduled worker and load tests.
4. Supabase Realtime may be evaluated for downstream fan-out, but it does not itself establish or maintain the upstream Upstox broker WebSocket session.

No hosting provider has been selected or changed. Do not shut down the existing Cloud Run service until the replacement runtime is deployed, tested, and explicitly approved.

### Verified OAuth and market data details

- OAuth state is random 32-byte hex, single-use, and expires after 10 minutes. It carries a connection generation so a callback started before disconnect cannot restore the connection.
- The token is encrypted with AES-256-GCM using a 32-byte canonical Base64 key held in Firebase Secret Manager today. The envelope is `{v:1,iv,tag,data}`. Keep the equivalent key in the replacement runtime's secret manager, not in Postgres or the browser.
- The token expiry helper sets the Upstox access-token cutoff at 03:30 Asia/Kolkata; the actual computed expiry must be persisted, not guessed from a fixed 24-hour TTL.
- The stream lease is renewed/expired in epoch milliseconds and disconnect marks it revoked.
- The pending LIMIT worker is opt-in gated, scheduled once per minute during the Indian cash-market window, fetches fresh quotes, and executes only eligible pending Delivery LIMIT orders. Preserve the explicit opt-in gate and worker cursor during migration.


## Atomic market-order RPC draft

Added `supabase/migrations/202611220002_paper_order_transactions.sql` with `public.execute_paper_market_order(...)`. It is a SECURITY DEFINER server-only PostgreSQL function that:
- locks the user's account row before checking idempotency and mutating balances;
- returns an identical prior order for the same user/key/fingerprint and rejects key reuse with a different fingerprint;
- validates the trusted server-provided instrument, side, product, quantity, paise price and quote age (maximum 15 seconds);
- enforces the shared virtual cash balance, reserved cash/margin, unreserved sell quantity, and 50-open-position cap;
- updates the product-specific equity position, cash, aggregate and product-specific realized P&L, account version, and immutable filled MARKET order in one database transaction;
- grants execution only to `service_role`; browser roles cannot call it.

This is the first transaction slice only. It does not yet implement pending LIMIT reserve/fill/cancel, option trades, account initialization, or quote/provider verification. The RPC trusts its caller for provider quote and identity validation, so only a trusted backend may call it. The RPC has not been executed against a staging database and has no runtime pass claim.


## Atomic Delivery LIMIT lifecycle RPC draft (2026-11-22)

Added `supabase/migrations/202611220003_paper_limit_order_transactions.sql` (draft only):

- `submit_paper_limit_order`: creates a Delivery-only pending LIMIT order; BUY reserves `limit_price × quantity` from shared unreserved cash, SELL reserves only unreserved Delivery shares. Idempotency key + fingerprint retries return the existing order; mismatched key reuse is rejected.
- `execute_paper_limit_fill`: server-only worker entry point; validates quote timestamp/age and limit-price crossing, locks account/order/position, applies the fill at the fresh quote price, releases the complete BUY cash reservation or SELL share reservation, updates cash/position/realized P&L and marks the order filled atomically.
- `cancel_paper_limit_order`: releases the remaining cash/share reservation and marks only a pending LIMIT order cancelled, under the same account-first locking discipline.
- All three functions are `SECURITY DEFINER` with a fixed search path and execute permission granted only to `service_role`. The trusted backend must validate identity and provider quotes; never expose service-role credentials to browser code.
- Intraday LIMIT remains disabled. No live broker order is submitted.

### Verified product behavior to preserve

1. Only long CE/PE MARKET BUY and SELL-to-close are enabled. Naked short options, futures, margin borrowing and live orders are disabled. SELL quantity cannot exceed the existing long position.
2. The instrument must be trusted provider/instrument-master data: NSE_FO or BSE_FO segment, NSE/BSE exchange, CE/PE type, valid instrument key and trading symbol, official lot size, tick size, expiry and strike.
3. Lots are whole numbers 1–10,000; quantity = lots × official lot size and is capped at 1,000,000. Price is integer paise and must align to the normalized contract tick.
4. Expiry is normalized to the India-local date. The contract expires at the exchange-local 15:30 cutoff; orders after that instant are rejected.
5. Quote instrument key must match, quote timestamp cannot be in the future, and quote age is at most 15 seconds.
6. The shared paper account must have valid cash/reservation/version values and zero reserved margin. A maximum of 50 distinct open derivative positions is enforced. Adding to an existing position at the cap is allowed.
7. BUY cash movement is negative premium; SELL cash movement is positive premium. The account's actual cash update is premium cash movement minus trade charges.
8. BUY cost basis increases by gross premium plus all BUY charges. SELL allocates the prior cost basis proportionally to the closed quantity, using integer half-up rounding (the entire remaining basis is allocated on a full close). SELL realized P&L = gross premium - allocated cost basis - SELL charges. Partial-close allocations must conserve the original paise cost basis over repeated closes.
9. Same idempotency key + same request fingerprint replays the original order without another debit; key reuse with a different fingerprint is rejected. Existing malformed positions or unsafe integer arithmetic reject the transaction before writes.

### Indicative fee schedule reproduced by current code

All values are integer paise, rounded with JavaScript `Math.round` at each fee component:

- Brokerage: ₹20 per executed order (2,000 paise).
- NSE exchange transaction: 0.03553% of premium turnover; BSE: 0.0325%.
- NSE IPFT: 0.0005% of premium turnover; BSE: zero.
- SEBI turnover: 0.0001%.
- Stamp duty: 0.003% on BUY only.
- STT: 0.15% on SELL only.
- GST: 18% on brokerage + exchange transaction + IPFT.
- Total charges are the sum of those rounded components. BUY total debit = gross + charges. SELL net credit = gross - charges and can legitimately be negative for very small premium turnover.
- These are explicitly indicative paper-simulation estimates, not a broker contract note.

The core schema draft was corrected to retain exchange and official lot-size metadata on derivative positions. The `net_credit_paise` field no longer rejects negative values, matching the existing fee helper's tested tiny-premium SELL behavior. This is a draft-branch-only change.

### Findings and draft fixes

1. **MARKET quote freshness:** the first draft trusted caller-provided `p_quote_age_ms` and did not reject a future `p_quote_timestamp_ms`. The RPC now derives current time from PostgreSQL `clock_timestamp()`, rejects future timestamps and quotes older than 15 seconds, checks caller age within a 2-second tolerance, and persists the database-computed quote age.
2. **LIMIT submit null-side edge case:** SQL three-valued logic meant a NULL side could fall through the original validation and enter the SELL branch. The RPC now explicitly rejects NULL `p_side`; it also validates account cash/reservation/version invariants before reserving.
3. **LIMIT fill quote clock:** the worker-supplied `p_now_ms` is now checked against database time (2-second tolerance), quote timestamp is checked against database time, and the stored quote age is database-computed.
4. **Options quote/expiry clock:** the caller clock is now required to be within 2 seconds of database time. Freshness and the 15:30 Asia/Kolkata expiry cutoff use the database clock rather than trusting the caller timestamp.

### Expanded disposable CI assertions added on the audit branch

- MARKET future quote, stale quote and caller-age mismatch must be rejected before order mutation.
- Two concurrent identical MARKET requests must produce exactly one order and one cash debit.

## Firebase third-party Auth integration — architecture correction (2026-11-22)

Supabase's hosted platform supports Firebase Auth as a third-party JWT provider. Keep the
existing Firebase login and pass the Firebase ID token to Supabase using the publishable
key; do not migrate or duplicate the user's login identity into Supabase Auth.

Firebase UID values are strings. Supabase's `auth.uid()` casts the JWT `sub` to UUID,
so the migration uses `auth.jwt()->>'sub'` and a private identity map instead:
- `paper_user_identity_map.firebase_uid` stores the exact Firebase UID.
- `paper_user_identity_map.supabase_user_id` is an internal UUID used by the relational
  tables. It is not a row in `auth.users`.
- `public.current_paper_user_id()` resolves the verified Firebase JWT subject to that
  internal UUID. It is SECURITY DEFINER, pins an empty search_path, and is executable
  only by authenticated/service roles.
- RLS policies compare each row's internal UUID to the helper result. Browser roles
  cannot read the mapping table itself.
- The server-side Firebase-to-Supabase resolver uses the same mapping and fails closed
  for UIDs that have not yet been migrated.

Before enabling client Data API access, register Firebase project ID
`zenura-ignite-technologies` in Supabase Authentication → Third-Party Auth → Firebase
(the value was read from the existing repository's public Firebase client config) and ensure every Firebase token
contains `role: authenticated`. Existing Firebase users require a controlled custom
claims backfill and token refresh; new users require the same claim on account creation.
Never expose the service-role key to the app. The existing gateway continues to verify
Firebase token revocation for its own server endpoints.

This removes the need to create synthetic email/phone identities or duplicate Supabase
Auth users. The identity map is created/imported as part of the controlled data migration.
No Firebase custom claims have been changed and no Supabase third-party Auth integration
has been enabled in the live project by this draft.


Official integration reference: https://supabase.com/docs/guides/auth/third-party/firebase-auth
