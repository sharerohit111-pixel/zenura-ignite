# Chat 63 — hosted CSP response-header staging gate

## Purpose and safety

This is a **staging-only proposal** for verifying the browser-enforced HTTP response-header policy that GitHub Pages cannot configure per site. It does not change the production host, DNS, deployment workflow, or production URL. The repository-root `_headers` file is consumed by Cloudflare Pages only when it is present in that project's static asset output directory; GitHub Pages does not interpret it as response-header configuration.

Do not connect a production domain or deploy this branch to production. Create a separate Cloudflare Pages project with a disposable staging name and no production custom domain. Configure its build output directory to the repository root (or copy `_headers` into the actual output directory if a build step is later introduced). The rule intentionally matches only `/markets/stocks/*`.

Cloudflare documents `_headers` syntax and its static-asset scope here:
- https://developers.cloudflare.com/pages/configuration/headers/
- https://developers.cloudflare.com/pages/how-to/add-custom-http-headers/

Important limitation: Cloudflare Pages `_headers` rules do not apply to responses generated by Pages Functions. This workspace is a static asset route for this test; if it is later served by a Function/Worker, that response handler must set and test the headers itself.

## Header policy

The staging rule mirrors the tested meta CSP and adds the HTTP-only `frame-ancestors 'none'` directive. It also sets:
- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`

The CSP intentionally contains no `'unsafe-inline'`, `'unsafe-eval'`, or wildcard source. Do not weaken it to make a test pass. If a real dependency is blocked, establish its provenance and update the allowlist through review.

## Staging verification procedure

1. Create a separate Cloudflare Pages project from this branch, with no production domain and no production deployment integration.
2. Confirm the deployed preview URL serves `/markets/stocks/index.html`.
3. Run the read-only header probe:

   ```sh
   curl -sSI "https://YOUR-STAGING-HOST/markets/stocks/index.html"
   ```

4. Run the hosted Chromium check from the repository root after installing the pinned Playwright version and Chromium:

   ```sh
   npm install --no-save --ignore-scripts playwright@1.56.1
   npx playwright install chromium
   S_TRADE_STAGING_URL="https://YOUR-STAGING-HOST/markets/stocks/index.html" \
     node --test market-gateway/test/hosted-response-header-security.mjs
   ```

5. Save the exact staging URL, deployed commit SHA, response headers, test output, and date in the PR evidence. Only then can HTTP header enforcement be marked PASS for that staging origin. Production remains BLOCKED until a separately approved hosting decision and a production-origin probe.

## Acceptance criteria

- Actual HTTP response contains a single effective `Content-Security-Policy` header.
- Header includes `frame-ancestors 'none'`, `object-src 'none'`, `frame-src 'none'`, `form-action 'self'`, and the exact dependency origins used by the workspace.
- Header excludes `'unsafe-inline'`, `'unsafe-eval'`, and wildcard source tokens.
- Chromium confirms the staging workspace cannot be embedded by an unrelated ancestor and the console reports the `frame-ancestors` refusal.
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, and the stated Referrer-Policy are present.
- No production deployment, domain change, DNS change, or merge is performed as part of this gate.

Until all criteria are demonstrated against a real staging URL, report hosted response-header enforcement as **BLOCKED**, not PASS.
